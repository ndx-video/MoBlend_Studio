# M3 — Bottom status bar + broker startup messaging

## Summary

Added a thin persistent status strip at the bottom of the app shell for broker lifecycle and error messaging. Replaced the old top-of-page “broker starting” banner and inline `home-status` text. Fixed broker-ready detection so an empty `{}` from `EngineHealth` no longer counts as connected.

## Root cause (missing startup banner)

`brokerReady` previously treated any health object with `status !== 'unreachable'` as ready. The Go stub `EngineHealth` binding returns `{}` when mocks are absent, which passed that check and let `loadProject` fire before the broker was up — producing the instant “Cannot reach broker…” error with no visible startup feedback.

## Changes

| Area | Detail |
|------|--------|
| `StatusContext.tsx` | `StatusProvider`, `useStatus()`, `isBrokerUp()`, `ensureBroker()`, auto-start on launch, 4s health poll |
| `StatusBar.tsx` | 24px footer: broker dot (unknown/starting/ready/unreachable), truncated message, `broker:8000` label |
| `AppShell.tsx` | Full-height column layout; `<StatusBar />` pinned to bottom |
| `App.tsx` | Wrapped in `StatusProvider`; Home/Projects/Suite route errors via `setStatus`; `ensureBroker()` before load flows |
| `client.ts` | Shorter fetch error (`Broker unreachable at …`) — detail lives in status bar |
| E2E | New nav test for `status-bar` / `status-bar-message` / `status-broker-dot` |

## `ensureBroker` fix

If startup is already in progress (`startingRef`), `ensureBroker` now **waits** (poll up to ~60s) instead of returning false immediately with “Engine is still starting…”. Launch effect checks health before calling `StartEngine` to avoid redundant spawns when Go already attached.

## User action

Restart `wails dev` (or rebuild) so the embedded app picks up `frontend/dist`. Watch the bottom status bar during first launch; if broker never comes up, use Suite Manager → Start Engine and check the `wails dev` terminal for Blender spawn errors.
