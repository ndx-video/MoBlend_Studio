# M3 — Black viewport despite live WS frames

## Summary

Editor showed **WS live**, ~10 fps, and advancing frame numbers, but the canvas stayed black. Investigation proved the broker was rendering valid JPEGs (~4.5 KB at 640×360); the bug was **client-side canvas painting** in the Wails WebView2, not Blender/EEVEE.

## Root cause

`useViewportStream` counted incoming FRAME messages for fps but painted with `createImageBitmap()` + per-frame `canvas.width` resets. In WebView2 this path often fails silently for Blender JPEG blobs; the fallback rarely ran before the next frame cleared the canvas.

## Fixes

| Change | Detail |
|--------|--------|
| `paintFrame()` | Primary path: `Image` + `URL.createObjectURL(blob)`; fallbacks: `createImageBitmap`, then data-URL |
| Canvas sizing | Only resize when `w`/`h` change (avoids clearing buffer every frame) |
| Stale paint guard | Monotonic `paintSeqRef` drops out-of-order async decodes |
| Preview loop | Frame counter `% 30` (scene is static); interval 120 ms (~8 req/s) to match EEVEE throughput |
| Editor readout | `painted N` / `paint err N` on `viewport-stats` test id |

## Verification

- Live probe: `ws://127.0.0.1:8000` → 640×360 JPEG, 4567 bytes, magic `ffd8`
- `npm run test:e2e` — 28/28 pass (mock + live broker)

## User notes

- Restart **`wails dev`** after `npm run build`
- If Blender/Node stay pegged: **Suite → Stop Engine**, kill stray `blender.exe` processes, **Start Engine** once
- Readout should show `painted` climbing; if `paint err` grows, double-click status bar and share log
